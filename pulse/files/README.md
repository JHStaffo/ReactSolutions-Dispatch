# Draw Box

Fast Track EMS's draw box, online. Dispatch credits a crew for a solicited call, each crew member signs in with an emailed code and draws a prize, and supervisors hand prizes out, manage the box, and run reports. The reports include per-employee prize value for taxes.

## How the draw works

- Each diminishing prize has two numbers, shown as **draws left / on hand** (for example 2/3 left). Every draw lowers draws left by one, even when the winner takes a cash bonus. On hand goes down only when the prize itself is taken. A prize's envelopes are its draws left, capped at what's on hand, so a prize at 0 of either is out of the drawing. The chance of drawing a prize is its envelopes divided by all envelopes left, so as valuable prizes run out during the month, candy and snack become more likely.
- On hand is the whole inventory in the safe (for gift cards, the brand counts). Each prize also has a **monthly** amount, and **Reset available** on the Inventory page sets every prize's draws left back to it. For example, 32 $10 cards on hand with a monthly amount of 8 resets to 8/32 left. Draws left and the monthly amount can be edited on each prize.
- Each prize has a **Diminishing** checkbox. Non-diminishing prizes (candy, snack) never run out, so their count only sets their odds and reset skips them.
- The home page, dashboard and inventory page all show the current dollar value of the box: every envelope left times its prize value. Prizes already won are not included.
- Prizes with **Cash bonus OK** checked let the winner choose "Issue as taxable cash bonus" instead, any time before the prize is handed out. The bonus equals the prize's value and is always taxable. The item or gift card goes back on hand, but the draw still counts against the prize's draws left. Supervisors mark it paid, and the tax report shows cash bonuses in their own column.
- Crew members aren't emailed the moment dispatch credits them. Every 2 hours, each team member with new draws gets one email listing them, so a credit undone in the meantime never sends anything.
- A credited draw can't be drawn right away: it waits 2 hours (Settings > Wait before drawing), showing on Home as "Available 3:15 PM". Its email goes out with the first batch after it opens.
- When the setting is on, each employee gets one email listing all of their draws that expire within the next 24 hours (checked hourly).
- Any other prize can optionally have **choices** (for example the kinds of candy bar in the Candy prize). The winner picks one after drawing, and that choice's count goes down by one. A diminishing prize with choices counts its choices as its envelopes. A non-diminishing prize with choices keeps its own count for the odds, but can't be drawn once every choice is out.
- Each gift card value (for example $50) is on hand as many times as there are brand cards in stock at that value. After winning a value, the employee picks a brand. Their card is held for them until they choose, so nobody else can take it.
- Draws happen on the server, are final, and are logged in the inventory change log.
- A prize moves from **won** to **received** when a supervisor marks it handed out. Tax totals count prizes by the date they were received, at the value they had when drawn.

## Permission profiles

Each team member has one permission profile, and admins edit profiles under Admin > Settings > Permission Profiles. Everyone can draw, pick a gift card brand and see their own prizes. A profile adds any of: Credit a call, Dashboard, Reports, Inventory, Locker map, Change or remove won prizes, Scope Check, Team Members, Settings, Audit log and Permission Profiles. A profile can have sub-profiles (EMT under Team Member, say), one level deep: a sub-profile gets everything its main profile allows plus what's checked for it. New features add a permission key in `PermissionProfile::GROUPS`; every profile starts without it. The starting profiles are Team Member, Dispatcher, Supervisor and Admin, matching the old fixed roles. `drawbox:make-admin` puts someone on the Admin profile and gives that profile every permission.

## Social Security numbers and dates of birth

Team Members can have an SSN and date of birth on file, for checks such as the OIG exclusion list (LEIE), which matches on name and date of birth and confirms with the SSN. The date of birth is encrypted with the same key and follows the same rules below: same two permissions, shown as month and day only (04/12/XX) until Show, every look and change audit-logged without the date, never in the API or exports, and an optional Date of Birth CSV column (4/12/1985 or 1985-04-12) that fills blanks only.

- **Stored encrypted** with AES-256-GCM using its own key, `SSN_KEY` in `.env` (not `APP_KEY`, so replacing the app key never loses them, and a copy of the database alone shows nothing). Beside it are only the last 4 digits (for the masked •••-••-1234) and a keyed fingerprint (HMAC-SHA256) that finds a number without decrypting every row: duplicates are refused, and a later OIG check can match on it. See `app/Services/Ssn.php`.
- **Permissions**, both on Admin to start and nobody else: *See SSNs* shows the last 4 on Team Members and a Show button that displays the full number for 30 seconds; *Add, change or remove SSNs* adds the SSN box to Add a Team Member, a Change/Remove form on each row, and the optional SSN column in the CSV import (fills blanks only, like phone). Nobody can give these out without having them.
- **Audit log:** every look, add, change, removal and refusal is logged with who and which Team Member, never the number.
- **Never sent anywhere:** the SSN columns are hidden from every JSON and array (so never in `/api/v1`), are in no CSV export, and a failed save never puts the number back in the form.
- **The key:** make it once with `php artisan drawbox:ssn-key` (it won't replace an existing key), then `php artisan config:cache`. Keep a copy of `SSN_KEY` somewhere safe and separate from the database backups: without it the saved SSNs can't be read. Until the key is set, the SSN boxes don't show.

## OIG Exclusions

Admin > OIG Exclusions (permission OIG Exclusions, Admin only to start) checks every active Team Member against the OIG's List of Excluded Individuals/Entities. **Check now** downloads the OIG's current `UPDATED.csv` (`services.oig.url`; the server needs outbound HTTPS to oig.hhs.gov), and `php artisan oig:check` runs on its own on the 15th of each month from the cron. Every check is kept: the list shows each date with "0 exclusions found" or the count in red, and a date opens every Team Member checked with their date of birth as MM/DD/XX and Not excluded, Excluded or Needs manual check.

Matching (`app/Services/OigExclusions.php`): first and last name (compound last names and Jr/Sr/II/III are handled), then date of birth. Same name and date of birth is **Excluded**; same name with a different date of birth is Not excluded; same name with no date of birth on either side is **Needs manual check**. The OIG file has no SSNs, so a match is confirmed on exclusions.oig.hhs.gov (search the name, Verify with the SSN). The result is recorded on the check: outcome, how it was checked (an SSN in the note is refused), and optionally the OIG result page as a PDF or picture, stored encrypted. Recording it updates the counts, and every check, manual check and file opened is in the audit log.

After each check of everyone (monthly or Check now), Pulse posts to the Slack channel picked on the OIG page: "OIG Exclusions checked: 42/42 Team Members", anyone on the list in bold at the top (marked new when they weren't on the last check), and anyone who needs a manual search. The latest download is kept at `storage/app/oig-leie.csv`.

**New Team Members** (added one at a time or by CSV) are checked against the kept copy of the OIG list (downloaded again when it's over 35 days old) and searched on the Virginia EMS provider search by legal name (`app/Services/NewMemberChecks.php`). One person is searched while the page waits; a CSV import is queued for `ems:run`. The person adding them sees anything off in red: an OIG match, not listed with our agency, another agency, or a search that couldn't run. These checks are kept on each page marked "New Team Member", skip Slack, and only run once that check has been run for everyone at least once.

## EMS Affiliations

Admin > EMS Affiliations (permission EMS Affiliations, Admin only to start) searches every active Team Member on the Virginia Office of EMS provider search (`services.va_ems.url`, https://vdhems.vdh.virginia.gov/emsapps/ProviderSearch.html; the server needs outbound HTTPS to it). **Check now** starts a check that `php artisan ems:run` picks up from the cron within a minute (a page can't wait for every search; the page shows progress), and `php artisan ems:check` runs one on its own every morning at 6. After each check, Pulse posts a summary to the Slack channel picked on the page: first any new unacceptable agency affiliations (all of them again on the 1st of the month), then Team Members newly affiliated with us, newly listed with another agency, and no longer affiliated with us (compared with the check before). Days with no updates post nothing. With no channel picked, it emails everyone with the permission instead. Searches are a second apart (`VA_EMS_PAUSE_MS`).

- **How it searches** (`app/Services/Ems/ProviderSearch.php`): the site is an Oracle APEX page with no API, so Pulse opens it, fills in the boxes it finds by their labels (Certification#, Last Name, First Name), presses Search, and reads the results table by its column headings. If the results have no agency column, it opens each matching provider's own page. **Try the search** on the page runs one search and shows what came back, including what Pulse found on the site, without saving anything. The site couldn't be reached while this was built, so try it first after deploying.
- **Matching:** by certification # when the Team Member has one, otherwise by first and last name. When a name search finds exactly one provider listed with our agency (Setting `ems_our_agency`, default FAST TRACK EMS, LLC, editable on the page), their number is saved and used from then on. Two or more matches with nobody at our agency show "More than one match" and save nothing; set the number on the Team Member's page.
- **Agencies:** names compare without punctuation or LLC/Inc endings. Every other agency a Team Member is listed with is kept with when it was first and last seen, and marked "No longer listed" when it disappears. A new one goes to **Needs review** (Acceptable or Unacceptable, with a note). Ticking "for everyone with this agency" also puts the agency on the **Acceptable agencies** or **Unacceptable agencies** list, and anyone listed with an agency on one of those lists is marked without a review (an agency is only ever on one list; adding it to one takes it off the other). Removing an agency from a list sends the affiliations it marked back to review. A person's own review always wins over the lists.
- **Accepted exclusion:** a Team Member not expected on the provider search (with a reason). They're still searched every time, and the first time they turn up everyone with the permission is emailed and they're listed under Needs review.
- **Email:** after a check, everyone with the permission gets one email when there's anything to look at (unacceptable affiliations, not listed with us, new affiliations, an accepted exclusion found, not found, or couldn't be matched).
- If the first three searches all fail (the site is down or has changed), the check stops and says why instead of failing everyone. Every check, review, list change, number and exclusion is in the audit log.

## ID Cards

Admin > ID Cards (permission ID Cards, Admin only to start) replaces the old Employee ID Generator (`enterdisc.html` + `makeid.php`). Pick a Team Member, the name on the card (filled in with their shown name), a job role and the D, I, S and C scores (0-100), and optionally a photo. The card is drawn by `app/IdCards/CardImage.php` the same way `makeid.php` did, as a 1080 x 690 JPEG: DISC bars top right, the photo box, the logo, the name, and the role on its colored band. Differences: the name is drawn once (the old script also drew a bold copy over the band when `arialbd.ttf` was present), a name or role too wide for the card is shrunk to fit, and a photo, when added, fills the box. The photo can be chosen, dropped on the page, taken with a phone camera, or reused from another of the Team Member's cards; it's moved and zoomed in a crop box shaped like the card's box, the preview shows it live, and the crop is saved on the card (`photo_crop`, fractions of the photo) so it can be adjusted later. The whole photo is kept (up to 1600 px). The font is Liberation Sans (same letter widths as Arial, SIL Open Font License, in `resources/id-cards/` with the logo), and the server's PHP needs the GD extension with FreeType.

Cards are kept on the Team Member: Admin > ID Cards lists the current ones (tick Show replaced cards for older ones), and Team Members shows an "ID card" link under each name. A card can be printed (a full-bleed page sized 3.375 x 2.125 in for the Entrust Sigma SL3: the image covers the card and runs 0.02 in past each edge; print with Margins None, Scale Default, single-sided) or downloaded as the JPEG. **New card for a new role or name** starts a new card from an existing one with its name, DISC scores, photo and crop (the photo file is copied), and marks the old card replaced (`replaced_by_id`). When a Team Member's shown name in Pulse no longer matches their card, the card page offers a new card with the new name. Job roles and band colors are edited under ID Cards > Job roles and colors (seeded with the old script's 16 roles and colors). A card copies its role's name and color when made, so editing a role never changes a card already made. Photos are stored privately in `storage/app/private/id-cards/photos`. Making, changing, deleting, printing and downloading cards, and role changes, are in the audit log.

## Forms and Slack

Dispatch forms replace Google Forms, the Google Sheet and Zapier. An admin builds each form under Admin > Settings > Form Editor (questions, choices, required or not) and picks the Slack channel it posts to. A form can also have its own Slack message, typed freely with `$answer1`, `$answer2` ... (and `$sender`, `$form`, `$date`, `$time`) filled in from the answers. When someone sends a form, Pulse saves it, then posts it to that channel right away. If Slack doesn't take it, the submission stays saved and `pulse:slack-retry` (every five minutes, from `schedule:run`) tries again up to five times; an admin can also press Post now under Admin > Forms > All submissions.

Slack is connected once, under Admin > Settings > Slack, with a Slack app's bot token (xoxb-...). The page has the app manifest and step-by-step setup. The token is stored encrypted with `APP_KEY`, so if the app key ever changes the token has to be pasted again. Public channels work straight away; private channels need `/invite @Fast Track Pulse` once. The server needs outbound HTTPS to slack.com.

Three permissions control it: Forms (fill out and send), Form reports (Admin > Reports > Form Reports: filter by period, form and sender, and once a form is picked by any of its own questions; total by any question, optionally split by a second one into a grid; Team Member and position only appear when the form asks about a Team Member; CSV) and Forms and Slack (build forms, see every submission, connect Slack). All start on the Admin profile only. Every send, test, edit and retry is in the audit log; the token never is.

Shared lists (Admin > Settings > Shared Lists, under the Forms and Slack permission) hold choices that grow over time, starting with Facilities. A "Shared list" question lets people pick an entry or type a new one, which is added to the list (matched ignoring capitals and extra spaces) unless the list is set to pick-only. Admins can bulk-add, rename, hide and remove entries; past submissions keep their own copy of the answer.

## RemoteLock

Admin > Settings > RemoteLock (permission "RemoteLock", Admin only at first) connects Pulse to RemoteLock with the client ID and secret of an OAuth application made in RemoteLock's developer portal (client credentials). They're stored encrypted with `APP_KEY`. The server needs outbound HTTPS to connect.remotelock.com and api.remotelock.com.

Pulse is the source of truth for each linked Team Member's name, email and whether they're active. Saving a Team Member sends the change right away: turning someone off deactivates them in RemoteLock (RemoteLock keeps the record and history), and deleting someone deactivates them first. RemoteLock can't reactivate a user, so turning someone back on makes a new access user with a new PIN. New Team Members (setting on the page, on by default) are added with their permission profile's door groups and the door PIN typed on the Add form (4 to 8 digits), or a random one when it's left blank; a linked Team Member's PIN can be changed from Admin > RemoteLock. PINs go to RemoteLock only and are never stored or logged in Pulse. if RemoteLock already has a user with the same email they're linked instead. Anything RemoteLock doesn't take is retried by `remotelock:sync` every five minutes from `schedule:run`.

The page also matches people already in RemoteLock to Team Members (suggested by email, then name), lists Team Members turned off in Pulse but still active in RemoteLock with one button to deactivate them, and sets door groups per profile. A sub-profile gets its main profile's door groups plus its own. Door groups are only given, never taken away; changing a profile's door groups doesn't touch people already in RemoteLock unless "Give profile doors" is pressed. Every action is in the audit log; the secret never is.

## Vehicle assignments and TV status boards

Dispatch > Vehicle Assignments sets, for each day and shift, every company truck's status (In service, Reserve, Special event, Out of service), level (the Scope Check levels) and crew (Team Members with an optional role), plus start and end miles and a note. "Copy the last shift" fills trucks not set yet from the last time that shift had assignments. Nobody can be on two trucks in the same or an overlapping shift. Team Members see their truck on Home.

- **Shifts** come from the shift list in Inspection Settings (`inspection_shifts`). Until that exists there is one all-day shift. Each assignment copies the shift name and times and the truck's name, so later edits don't change history.
- **Out of service** is the Inspections flag (`inspection_subjects.out_of_service_at`). A down truck can only be set to Out of service, unless an override on the Trucks page lets it run (for a date range or until ended; "assignments and every rotation rule", or "by hand only"). Overrides keep their history.
- **Backup trucks** are marked on the Trucks page and offered first when a front-line truck is down.
- **Status boards** (Admin > Settings > Status Boards) are TV pages at `/board/{token}`: no sign-in, refresh themselves, plain HTML for a Fire TV Stick (Silk) or a Google TV kiosk browser. "Make a new link" stops the old one. Panels are classes implementing `App\StatusBoards\Panel`, listed in `config/status_boards.php`; other modules add theirs there.
- **Reports:** Admin > Reports > Vehicle Assignment Reports (by truck, by Team Member, CSV). API: `/api/v1/vehicle-assignments` (see docs/api.md).

- **Rotation protocols** (Vehicle Assignments > Rotation protocols, permission "Rotation protocols"): named sets of rules, each "must" (never broken) or "prefer" (weight 1 to 5), covering chosen trucks or all. The rule types are in `App\Fleet\Rotation\RuleTypes` (levels, coverage, use and balancing, shifts/days/dates, crews, backups and special events); `App\Fleet\Rotation\Planner` checks the must rules, scores the rest, fills the protocol's trucks for the shift, then adds trucks for "keep at least N on the road". "Suggest" on the assignments page shows each choice with its reasons; "Use these" saves it (filling trucks not set, or replacing). An out-of-service truck is used by a protocol only if its override covers everything or one of that protocol's rules for it.

Permissions (Admin only at first): "Rotation protocols", "See vehicle assignments", "Assign vehicles", "Vehicle assignment reports" and "Status boards".

## Vehicles (license plate camera)

The Vehicles menu uses the Turing (turing.ai) license plate reader. Turing pushes each vehicle read to `POST /api/v1/lpr/turing` as it happens (their "vehicle" webhook at the "processed" stage, which carries `metadata[].license_plate_text`). Turing has no screen for this: email support@turingvideo.com with the endpoint URL and the secret from Vehicles > Camera settings ("Make a secret"; stored encrypted with `APP_KEY`, shown once). Every request must carry `x-turingvideo-signature`, the HMAC-MD5 hex of the raw body with that secret, or it's refused (401) and the refusal is in the audit log. Turing waits 5 seconds and retries only on 429/5xx, so a repeated `event_id` is answered 200 and skipped.

Permissions (Admin only at first): "Vehicles" (on property now, every plate read), "Manage vehicles" (vehicle list, cameras, the Turing secret, counting settings) and "Arrival times" (Team Members' arrival and leave times, company vehicle trips, CSV).

- **Vehicle list:** company vehicles (unit number) and Team Members' own cars, by plate (letters and numbers only, upper case). An unknown plate can be added straight from its read; its earlier reads and stays are then filled in. A read that doesn't match exactly but looks like exactly one listed plate (O/0, I/1, B/8, S/5, Z/2, G/6) is matched and marked.
- **In or out:** cameras appear on Camera settings after their first read, set to "Both ways" (in when the plate isn't on property, out when it is), "Entering only", "Leaving only" or "Ignore". The same plate at the same camera within the repeat window (3 minutes) is a repeat. A stay with no exit after the longest stay (26 hours) is closed as "never seen leaving" (by the next read or by `vehicles:close-stale` hourly from `schedule:run`), so the next read is an arrival.
- **Pictures:** Turing sends only a link to each read's snapshot, and its links stop working, so Pulse downloads the picture right after the read arrives (with a 320 px copy for lists) into `storage/app/private/plate-snapshots/`. Any it couldn't get are retried by `vehicles:snapshots` every five minutes (5 tries, within 2 days). Pictures older than "Keep pictures (days)" on Camera settings (365) are deleted by `vehicles:prune-snapshots` each night. They're only shown to people with the Vehicles permission. The server needs outbound HTTPS to Turing's picture host.
- **History:** each read keeps the vehicle and Team Member it matched at the time; stays (`plate_visits`) are what the arrival report uses. Plate reads themselves are not in the audit log (they're their own log on the On property page); every change people make is.

## Inspections and check sheets

Electronic check sheets for trucks, stations and equipment (`app/Inspections`, `routes/inspections.php`, under the Equipment menu). Permissions (Admin only at first): "Inspections" (do checks, report problems, see their own checks), "Deficiencies" (every check and deficiency, assign and fix, out of service and back, skip a due check), "Manage inspections" (check sheets, schedules, what gets checked, shifts, notices) and "Inspection reports" (reports, CSV and the dashboard).

- **What gets checked:** trucks are the company vehicles on the Vehicles list (one `inspection_subjects` row per vehicle, made automatically; turning a vehicle off turns it off here). Stations and equipment are added by name. `asset_id` and `facility_id` are kept for the Assets and Facilities modules.
- **Check sheets:** questions are Pass/Fail, multiple choice (with the choices that are a problem), a number with an OK range, a count (how many there should be), text or photo. Each can be required, need a photo on a problem, take the truck or equipment out of service on a problem, and be shown only when an earlier answer is a given value (for a number or count: "Problem" or "OK"). A sheet is for trucks, stations, equipment or anything, optionally only some of them, and can be copied as a template.
- **Importing paper check sheets:** on Check Sheets, upload a PDF or up to 5 photos of a sheet in use now. `inspections:import` (every minute from cron) has Claude read it, using the Anthropic key in Admin > Settings, into a check sheet that stays turned off until someone goes over it in the builder and turns it on. AI's notes on anything it guessed show on the list and in the builder. Each read counts toward the uploader's monthly AI limit, the same one as the Training builder tools (Admin > Reports > Training AI Usage), and uploads stop once it's reached. Files are kept under `storage/app/private/inspection-imports`.
- **Doing a check:** on a phone, with a drawn signature (stored as a PNG under `storage/app/private/inspections`). Answers are kept on the device until it's submitted. Each answer copies its question's wording, so editing a sheet never changes history. The check records its shift, from the editable shift list in Admin › Settings › Inspection Settings (a shift that ends at or before it starts runs past midnight; days can be limited).
- **Schedules:** a sheet is due every shift (a set time after each shift starts, optionally only some shifts), daily, weekly, monthly or every few days by a set time, for one subject or every one it's used for, and assigned to anyone, everyone in a profile, or one Team Member. `inspections:schedule` (every 5 minutes from `schedule:run`) makes the due checks (`inspection_dues`), skips them while the subject is out of service, marks unfinished ones missed when the next period opens, emails the assigned Team Member a reminder before the due time, and once overdue emails them and posts the list to the inspections Slack channel. A finished check counts for the due check it was started from, or the open one for that sheet and subject. Deficiencies can skip a due check with a reason.
- **Dashboard and reports:** the dashboard shows today's done, due, overdue and missed checks, open deficiencies and readiness per truck. Inspection Reports gives on-time %, late, missed and skipped per check, checks by Team Member, deficiencies found and fixed with the average time to fix, and CSVs of checks, due checks and deficiencies. The API is under `/api/v1/inspections` (docs/api.md).
- **Deficiencies:** every problem answer opens one, or adds to the one already open for the same question on the same truck. New ones post to the Slack channel and email the Team Members picked in Inspection Settings. Each keeps a corrective action log (status, assignee, notes, photos); marking it fixed needs a note and can put the truck back in service.
## Service Desk

Internal support tickets (`app/ServiceDesk`, `routes/service-desk.php`). A Team Member picks a category, writes a subject and details, sets a priority (the category's usual one to start), can attach up to 10 photos or files (20 MB each, kept on the private disk under `storage/app/private/service-desk`) and can say which truck it's about. The category routes the ticket to a department; the department's handlers get an email (if turned on) and its Slack channel gets a post.

- **Statuses:** New, Assigned, In progress, Waiting on submitter, Resolved, Closed. Assigning a new ticket makes it Assigned. A reply from the submitter on a Waiting or Resolved ticket puts it back to In progress. Resolving or closing needs a resolution note. The submitter can reopen a resolved ticket; `service-desk:close` (daily from `schedule:run`) closes it after the close window (7 days).
- **History:** every reply, internal note (handlers only, never shown to the submitter) and change (assigned, reassigned, moved, priority, status, escalated, closed) is an entry on the ticket. Emails go to the submitter on handler replies and on Waiting, Resolved and Closed; to the assignee (or the department's handlers when no one is assigned) on submitter replies; to a new assignee and a new department's handlers.
- **Escalation:** `service-desk:escalate` (every 15 minutes) escalates a New, Assigned or In progress ticket no handler has touched for its priority's hours (Urgent 1, High 4, Normal 24, Low 72; 0 = never). It emails the department's leads (or all its handlers if none are leads), everyone with Manage all tickets and the assignee, and posts to the department's Slack channel. It repeats after another full wait, up to 3 times.
- **What a ticket is about:** `App\ServiceDesk\Links::TYPES` lists the kinds of records a ticket can point to (company vehicles now). Assets, facilities and work orders add one entry each when they're built; tickets keep `related_type`, `related_id` and the name at the time (`related_label`).

Permissions (Admin only at first): "Service Desk" (submit and follow their own tickets), "Work tickets" (work queue and dashboard for the departments they're a handler of), "Manage all tickets" (every department, delete, every escalation), "Service Desk reports" (Admin > Reports) and "Service Desk settings" (Admin > Settings: departments, handlers and leads, Slack channels, categories, escalation hours, close window). Every action is in the audit log.

## Supplies

The Supplies menu keeps the supply catalog and where every item is. It's part 1 of the Supplies and Assets plan (ordering, pharmacy and drug boxes, controlled substances, assets and maintenance come in later parts).

Permissions (Admin only at first): "Supplies" (search, see stock everywhere, record supplies used), "Restock and count supplies" (receive, move, restock, count, expired/damaged/adjusted, history and CSV), "Manage supplies" (catalog, places, layouts, minimums and maximums, settings, imports, count schedules and surprise counts) and "Approve supply count differences". Each place page also has "Move several items to another place" (`supplies.places.move-out`): how many of each item, or everything, in one step, earliest expiry first, all or nothing.

- **Places:** supply rooms and pharmacies (tick any mix of Main supply, Remote supply, Main pharmacy, Remote pharmacy), stations, trucks (linked to a company vehicle on the Vehicles list; "Add them as trucks" makes one per vehicle), and bags or kits inside another place. A place with stock can't be turned off.
- **Stock** is kept per item, place, lot and expiry (`supply_stock`). Every change is a row in `supply_transactions` that is never edited; mistakes are fixed by another change. Bulk stock leaves a place earliest expiry first. Items marked "Track each piece by serial number" move one serial at a time (`supply_units`).
- **Numbers:** barcodes, QR codes, vendor part numbers and (once "We have RFID" is on in Supplies settings) RFID tags. A scan or typed number that matches one exactly opens the item; so does Pulse's own label number `SUP-<id>`. Labels print with a barcode or QR code (drawn in the browser by JsBarcode and qrcode-generator from jsDelivr). Phone camera scanning uses html5-qrcode from jsDelivr.
- **Minimums:** each optional: a place's minimum and maximum (the maximum is what Restock fills to; copy one truck's list to the others), a minimum for all supply rooms together (main and remote supply rooms), and a minimum everywhere. Low and expiring lists both, with a nav count. `supplies:alerts` at 7 AM (from `schedule:run`) posts a summary to the Slack channel picked in Supplies settings, and emails Team Members with Manage supplies if that's turned on, only on days something needs attention.
- **Import** (Supplies > Import): a supply list or a par sheet for one place, from CSV, Excel (.xlsx, read with ZipArchive, no extra package), a PDF or a photo. CSV and Excel files with a Name or Item column are read on upload; anything else is read by Claude when the cron job runs `php artisan supplies:import` every minute (same Anthropic key as Protocols, answer held to a JSON schema). Every upload waits on a review page where rows can be fixed or unticked, and nothing is saved until Save. Supply list rows match an item by barcode, then name (blank cells leave values alone). Par sheet rows are matched to the catalog by name, code, other name, words in common or close spelling, or added as new items, and set the place's minimum and maximum. Rows post as one JSON field, so long sheets aren't cut off by PHP's `max_input_vars`.
- **Layouts (planograms):** each place can be drawn as racks, cabinets, compartments or drawers (`supply_sections`), each a grid of shelves (top to bottom) and bins (left to right) with its own words ("Drawer"/"Slot") and an optional photo. Items go in bins (`supply_bins`; an item can be in many bins and a bin can hold many items) by clicking a bin or dragging an item onto it. Item pages, searches, count sheets and the API give a walking label ("Medic 12 › Compartment 3, Shelf 2, Bin 1") and the drawing with the bin lit. Bin labels print with each item's barcode.
- **Counts (audits):** a count (`supply_audits`, `supply_audit_lines`) records what Pulse expected and what was there, and changes nothing until it's approved. Counts are blind by default (expected numbers hidden). Each difference needs a reason (used and not recorded, missing, expired, damaged, moved, arrived and not received, earlier count wrong, other), and approving turns it into stock changes in the history (expired and damaged as those types). Serial-tracked items are counted by ticking serial numbers; pieces not found become "lost" on approval. A count where everything matched is done at once. Supplies Settings can turn off the separate approval (counters then approve their own) and blind counts. Schedules make a count come due for one place or every place of a kind (every truck) weekly, monthly, quarterly or yearly, due the last day of the period; managers can start a surprise count. `supplies:audits` at 6:45 AM makes due counts and emails whoever a count is for when it comes due, a few days before (setting), and once when overdue; overdue counts and counts waiting for approval are added to the daily summary and the Supplies nav count.
- **Sealed bags** (Supplies > Sealed bags): heat-sealed bags on the trucks (airway bag 3 and so on). A bag type is a serial-tracked catalog item (`supply_kits`, contents in `supply_kit_items`), so trucks carry them as pars and they show in counts, Low and expiring, search and the API. **Fill bags** takes the contents out of a supply room (earliest expiry first) and gives each bag a serial number (`B3-261116-01`) and an expiry, which is the earliest expiry inside. A card prints for each bag to go inside: bag number and name, the expiry in large type, the serial as a barcode, who filled it and when, and the contents. An in-date sealed bag counts as complete. **Opened** records a bag used on a call and puts anything unused back in a supply room. Scanning a card opens the bag.
- **Orders** (Supplies > Orders; permissions "Order supplies" and "Approve supply orders", Admin only at first): vendors (`supply_vendors`) with account #, contact, order email, phone and website, and each item's part number, price and preferred vendor (`supply_vendor_items`; scanning or typing a vendor part number finds the item). **Needs ordering** lists items below a supply room or everywhere minimum, suggesting enough to get back to the minimum after what's already on order plus the item's "extra to order", and ticked items go onto each vendor's draft. Orders (`supply_orders`, `supply_order_lines`) go draft, then waiting for approval when the total is over the amount in Supplies settings (blank = no approval), then ready to send: emailed from Pulse (the order in the email, a CSV of the lines attached, replies to the sender), or marked printed, phoned in or ordered on the vendor's website with their order #. The order prints (or saves as a PDF from the browser) with the address and billing details from Supplies settings. Receiving all or part puts stock in a supply room with lot and expiry at the order's price (`supply_transactions.order_id`); the rest stays open as backordered until it arrives or the order is closed. Orders waiting for approval show in the Supplies nav count for approvers, and waiting or 2-week-old open orders go in the daily summary. **Supply Spending** (Admin > Reports) totals what was received by month, vendor, category or item, with a CSV of every line. Vendor part numbers typed on items before this became vendors, and Bound Tree and Life-Assist are added if missing.
- **Requests** (Supplies > Requests; permission "Ask for supplies", Admin only at first, for Team Members to have): ask for supplies for a truck, station or other place from the approved catalog, starting from that place's usual items with what's short. Requests (`supply_requests`, `supply_request_lines`) go on the restock list for anyone with Restock and count supplies, who marks them picked and sends them from a supply room (the stock moves then, earliest expiry first), and the requester marks them received; they're emailed when it's picked, sent or declined. Requests worth over the amount in Supplies settings (at cost), or with an item in a category ticked "Always needs approval", wait for "Approve supply orders and requests". `supplies:requests` runs hourly: it keeps one automatic restock request per truck, station or bag below a minimum (filling back to the maximum; done once sent) and adds supply room shortages to the preferred vendor's draft order; both can be turned off in Supplies settings. Orders over a second amount need two different approvers.
- **Forecast** (Supplies > Orders): use a week over the last 90 days (what left the supply rooms, less what came back), weeks of stock left in the rooms, and an amount covering the weeks set in Supplies settings. **Supply Value** (Admin > Reports): on-hand value at cost by place and by category.
- **Pharmacy and drug boxes** (Supplies > Drug Boxes; permission "Drug boxes", Admin only at first): catalog items can be marked as medications with strength, volume in each vial or container (`volume`, such as "1 mL"), form, route, whether they're controlled (DEA schedule) and whether they're pharmacy only (`pharmacy_only`: `App\Supplies\Stock` refuses to receive or move them anywhere but a pharmacy, a place inside one, or a drug box, and the item page warns if some is already stored elsewhere); medications always track lots and expiry. Drug box types (`supply_box_types`, as many as needed, made blank or as a copy of another) each have their own layout of compartments, trays or panels drawn as a grid of squares up to 30 x 30 (`supply_box_sections`) and their own contents, each item in a block of squares from its top-left square (`row`, `col`, `width` across, `depth` down; blocks can't run off the tray or partly cover another, and items sharing a block share its size) with how many (`supply_box_type_items`). The editor lights up the block while you type its size, red when it won't fit. Each drug box (`supply_drug_boxes`) is a place of its own (kind `box`, hidden from the place lists) so its meds keep their lots and expiry; the place's parent is where the box is. Restocking counts what's really in the box (missing meds are recorded as used on the call that opened it), optionally takes out expired and expiring meds, fills it from a pharmacy (places ticked Main or Remote pharmacy) earliest expiry first, and records the new seal or seals (each box type sets how many seals its boxes get, 1 by default, in `seal_count`; they are stored together as "S-1, S-2", and no seal number can be on two sealed boxes). Every sealing needs the sealer's own PIN (the same hashed PIN as the controlled substance witness PIN, set at Supplies > Drug Boxes > My PIN, with the same lockout after 5 wrong tries). A box the pharmacy can't fill is only sealed when the person ticks that they wrote what's missing on the outside of the box and gives a reason; it's stored in `missing` and `missing_reason`, shows as Incomplete, and puts its truck in Needs attention until it's sealed full. A box type can also have a spot for a whole box of another type (`supply_box_type_slots`, same squares as items, no loops), such as a Narcotics box inside an ALS box. Putting a sealed box inside makes the outer box its place's parent, so it rides along onto trucks; its meds and vials are listed on the outer box and count toward its earliest expiry, but never toward the outer box's par. Controlled meds can be on a box type's list (its par); `DrugBox::shortages()` counts them by in-stock vials in the box (`controlled` = true on the row), restocking never moves them (they go in under Controlled Substances) and a short controlled line makes the box incomplete. An outer box is only sealed complete when each spot has a sealed box in it, and a box on a truck can't have boxes put in or taken out. Only sealed boxes go on trucks. An opened box is swapped for a sealed one with the reason and PCR or call number, and goes back for restocking. Every step is in the box's own history (`supply_drug_box_events`) and the audit log; open boxes are in the daily supplies summary and expiring meds in boxes show in Low and Expiring. **Drug inventory import** (Supplies > Drug Boxes > Drug inventory import, a one-time load): uploading the pharmacy workbook (Medications sheet, * = controlled; Drug Box Equipment; one sheet per "ALS/BLS Drug Box N" with its seals and asset tag; decommissioned sheets and vendor numbers left out) makes a draft only (`supply_imports` kind `drugs`). A person checks the names against the catalog, then types the lot, expiry and count of every vial section by section and marks each reviewed; finalizing (the finalizer's own PIN, since it seals the boxes, plus controlled substances admin and a witness PIN when there are controlled vials; "Save for later" keeps a half-reviewed import to Continue any time) puts shelf stock in the pharmacy, receives each controlled vial into the vault on its own record and moves box vials into their box, and makes each box with its seals, asset tag and notes (spare and narcotics seals). `App\Supplies\OpeningInventory`.
- **CSV:** catalog, stock and history exports. API: `/api/v1/supplies/*` (see docs/api.md), with the `supplies` token ability.
- **Controlled substances** (Supplies > Controlled Substances; permissions "Controlled substances" for crews and "Controlled substance admin", both Admin only at first): every vial is its own record (`cs_vials`) with a Pulse ID barcode label (CS000012), serial, lot, expiry and amount. Its chain of custody (`cs_entries`) is append-only: the model refuses updates and deletes, and mistakes are fixed with correcting entries that say what changed. Vials are received into a room ticked "Controlled substance vault", then moved to narcotic pouches, drug boxes or trucks, or assigned and handed off between Team Members (the person taking the vial confirms with their PIN), returned, sent back or destroyed. Given and wasted amounts carry the PCR number and patient initials, and must add up to what was in the vial. Each Team Member sets a witness PIN (4 to 8 digits, hashed; an admin can clear it); each action needs one or two people as set in Controlled Substance Settings (by default only a full dose with nothing wasted needs one person). Counts (`cs_counts`) are done with two people by scanning; a mismatch stays red on the overview until a Controlled substance admin writes it up, and the count's page shows every entry since the last matching count. Reports (Admin > Reports > Controlled Substances): per drug, per Team Member, discrepancies and an inventory snapshot as of any date, each with CSV and print or PDF. Records are never deleted. Controlled items can't be moved as bulk stock; on a drug box list they set a par counted by vial; expiring vials, overdue counts and open discrepancies are in the daily supplies summary.

## Assets

Equipment > Assets tracks anything worth tracking one at a time (stretchers, power loads, monitors, LUCAS devices, radios, laptops and the trucks themselves). It's part 6 of the Supplies and Assets plan; code lives in `App\Assets` and `routes/assets.php`. Permissions: "Assets" (see them, their files and history), "Check out, check in and audit assets", and "Manage assets" (add and change, status, costs, files, imports, settings and reports). All three start on Admin only.

- **Records** (`assets`): tag (next number after the prefix in Asset Settings, e.g. A00012, or typed), name, type (`asset_types`), make, model, serial or VIN, RFID tag number (for part 10), vendor, purchase date and price, warranty, notes, photo. A company vehicle from the Vehicles list is linked (`vehicle_id`), not copied: price, files and maintenance live on the asset, plate reads stay in Vehicles.
- **Status and place**: Available, Assigned, Damaged, Out of service, In repair (shop, due back), Loaned (to a person or agency, due back), Missing, Lost, Stolen, Sold (sale price), Disposed and Retired (reason and disposal method). Where it is: a place (truck, station, room, bag) or with a Team Member. Past due-back dates and missing assets show in the Equipment menu count and the daily supplies summary.
- **Timeline** (`asset_events`): added, changed (from and to), every status change and move, check-out and check-in, repair and maintenance costs, files, audits and service requests. A Service Desk ticket can be about an asset (Links type `asset`).
- **Files** (`asset_documents`): invoices, manuals, inspection reports, titles, registrations, warranties and photos, with who added them and when.
- **Check out / in** by scanning tags (USB or Bluetooth scanner, or the phone camera) to a Team Member or a truck, with an optional due-back date.
- **Audits** (`asset_audits`): pick a truck or station, scan what's there. Pulse lists what wasn't found, what was found but listed elsewhere, and unknown codes; a manager can mark what wasn't found as Missing, or move what was found to the audited place.
- **Labels**: barcode or QR, printed from the list (tick assets) or an asset's page.
- **Value**: Asset Settings turns depreciation on or off. On: straight line from the purchase date over the type's useful life (or the asset's own) down to the salvage value or percentage, shown as book value.
- **Reports** (Admin > Reports > Asset Reports): by status and location, value by type, repair and maintenance cost per asset, and lost, stolen, sold, disposed and retired in a period, each with CSV and print.
- **Import** (Equipment > Assets > Import): CSV and Excel lists with a Name column are read on upload; PDFs, photos and other layouts are read by AI from the scheduler, using the same importer as supply lists. Rows are reviewed before saving; a row with an existing tag (or the same serial and name) updates that asset.
- API: `/api/v1/assets` (see docs/api.md), with the `assets` token ability.

## Maintenance and buildings

Equipment > Work Orders, Coming Due, Maintenance Plans and Buildings. It's part 9 of the Supplies and Assets plan; code lives in `App\Maintenance` and `routes/maintenance.php`. Permissions: "Maintenance" (see everything, make work orders, and work the ones assigned to them or to nobody) and "Manage maintenance" (every work order, plans, buildings, reports and settings). Both start on Admin only.

- **Buildings** (`facilities`, `facility_documents`): each station, office and building with its address, phone, contacts, alarm company and account number (no codes), utility accounts, landlord and lease dates, notes, files (lease, insurance, permits, floor plans, photos), the supply places in it (`supply_locations.facility_id`), the assets kept there, its maintenance and work orders, and its checks. "Set up checks" adds it to Inspections > What Gets Checked as a station, so check sheets for stations cover it. Leases ending within 90 days are in the daily summary. A Service Desk ticket can be about a building (Links type `facility`).

- **Maintenance plans** (`maint_plans`): for one asset, every asset of a type, or a building; due every so many days, weeks, months or years, miles, or engine hours, whichever comes first (buildings by time only), with how far ahead counts as "due soon", a usual vendor, cost and assignee, and instructions copied onto each work order.
- **Coming due** (`maint_dues`): one row per asset or building a plan covers, with when it was last done and when it's next due. Type plans pick up new assets each morning. History from before Pulse is typed in on the plan's page ("Set last done"). Overdue and due-soon items show on Coming due, the asset's and building's pages, and the Equipment menu count.
- **Work orders** (`work_orders`, `work_order_parts`, `work_order_notes`, numbered WO-00012): made from a plan (by hand, or by themselves each morning when Maintenance Settings says so, on by default), from a problem found on a check ("Make a work order" on the deficiency, which then shows Being fixed), from a Service Desk ticket, or by hand. Each has a priority, assignee, vendor, due date, notes and files, and parts taken out of supply stock at a chosen place (bulk items; their cost comes from the item). "Put back" returns a part to the shelf it came from.
- **Done**: records what was done, labor and vendor cost, the vendor, and miles and hours. The plan starts over from that day and reading, a problem from a check is marked fixed (and the truck or station can go back in service), the ticket gets a note, and the total goes on the asset's timeline and its repair and maintenance cost.
- **Daily run**: `maintenance:run` at 6:50 AM (from `schedule:run`) makes the work orders and posts a summary to the Slack channel in Maintenance Settings, and emails it to Team Members with "Manage maintenance" when that's on.
- **Reports** (Admin > Reports > Maintenance Reports): maintenance history (for everything, or one asset or building), cost per asset and building with cost as a percent of the purchase price, and open work orders with overdue and due-soon plans and open problems from checks, each with CSV and print.
- API: `/api/v1/maintenance` (see docs/api.md), with the `maintenance` token ability.

## RFID

Supplies > RFID, part 10 of the Supplies and Assets plan; code lives in `App\Rfid` and `routes/rfid.php`. Everything RFID shows only while "We have RFID" is ticked in Supplies Settings (`supplies_rfid_enabled`, off by default); with it off the page and API answer 404 and the tag fields are hidden (an asset that already has a tag still shows it). Permission: "RFID", Admin only to start. Pulse doesn't talk to a reader directly: any handheld that types tags like a keyboard, or exports its reads as a list or CSV, works.

- **Tags** (`rfid` on `assets`, `supply_units`, `cs_vials` and `supply_locations`): scan a tag and say what it goes on: an asset (by tag or serial), a serial-tracked piece (by serial), a controlled vial (by Pulse ID or serial), or a place (a pouch, bag, drug box, truck or room). Tags are stored without spaces or dashes, in capitals, and one tag can only be on one thing. Item-level tags (an RFID code on a catalog item) are still looked up too. "Look up a tag" says what a tag is on and where Pulse has it, with a button to take the tag off.
- **Sweeps** (`rfid_sweeps`): pick the place, then scan with the reader in keyboard mode, paste its list, or upload its CSV or TXT export. Pulse compares the reads with the tagged things it has at that place and the places inside it (three levels, so a truck sweep covers its bags and pouches): **where they belong**, **missing** (should be there and wasn't read), **listed somewhere else** (read here but Pulse has it at another place, with a Team Member, or used), and **unknown tags**. A sweep only reports; it never moves anything, so fix stock the usual way. Each sweep is kept and is in the audit log with its counts and what was missing. Controlled vials in a vault or drug box can be swept the same way as an audit alongside the witnessed count.
- API: `/api/v1/rfid` (see docs/api.md), with the `rfid` token ability, for a future reader app.

## Protocols

The Protocols menu holds the protocol book. Each protocol is a flowchart (boxes and arrows, drawn in the browser by Mermaid from a CDN, so there's still no build step) plus color-coded sections like Goals, Treatment, Special Considerations and Pediatrics. Boxes have a type (red action, white step, yes/no diamond, blue "Treatment per", yellow note, green Exit, black Transport), optional level badges (E, A, I, P, the pediatric stroller, M for Medical Control) and can open another protocol. Arrows go one way, both ways, or are a dotted line with no arrowhead, with an optional label (YES, NO, or anything). Mermaid lays the chart out automatically; when that doesn't line up, "Arrange boxes myself" in the builder switches the chart to hand placement: boxes are dragged in the preview (starting from where Mermaid put them) and each arrow can leave and enter a chosen side. Hand-arranged charts are drawn by `public/js/protocol-chart.js` with square-cornered lines. Text takes `**bold**`, `__underline__` and `- ` bullets; everything else is escaped.

Every change is a version. Builders (Build protocols) save drafts and send them for approval; the Medical Director (Medical Director permission) approves by typing their name, or sends it back with a note. Team Members (Protocol book) only ever see the approved version, which stays in the book while a revision is worked on, and approved versions are never edited. The book can be opened whole, by category, by age group (Infant, Pediatric, Adult) or one protocol at a time, searched, and printed one protocol per page. All three permissions start on the Admin profile only. Protocol categories (the book's chapters) are added, renamed, ordered and deleted in Admin > Settings; a category in use can't be deleted. `ProtocolVersion::toApi()` is the shape the future mobile API will serve.

Protocols > Build protocols > Import from PDF or photo takes one PDF or up to 10 photos (JPG, PNG, WebP; photos over 3.5 MB are shrunk with GD). The cron job runs `php artisan protocols:import` every minute: it sends the file to the Claude API (`anthropic-ai/sdk`, model `claude-opus-5-5`, answer held to a JSON schema) and asks for the protocols that start on the next two pages, so a whole book is read two pages a minute. The PDF is cached between requests, so the repeat reads cost a tenth. Each protocol found is saved as a version 1 draft laid out like the page (hand-arranged layout), categories are matched by name or added, and when the upload is finished, Exit and Treatment boxes are linked to the protocols they name. Anything Claude wasn't sure of shows as a note on the upload. A busy API is retried up to 5 times with a growing wait; other errors stop the upload with a Try again button. PHP's upload limit on cPanel defaults to 2 MB, so raise `upload_max_filesize` (25M) and `post_max_size` (30M) for the domain in cPanel > MultiPHP INI Editor. It needs an Anthropic API key: an admin pastes it in Admin > Settings (checked with Anthropic, stored encrypted with the app key), or `ANTHROPIC_API_KEY` goes in `.env`; a key saved in Settings wins. `php artisan protocols:import --all` reads everything waiting right away.

`php artisan db:seed --class=ProtocolSampleSeeder` loads the Cardiac Arrest protocol as a draft example. `php artisan protocols:load-sample` does the same, or, when Cardiac Arrest already exists, puts the arranged sample into its draft (starting a new version if it is approved, taking it back if it is waiting for approval) and keeps links builders set on its boxes.

## Wellness

The Wellness menu is its own module (`app/Wellness`, `routes/wellness.php`, tables starting `wellness_`). It only reads `users`, and nothing outside it reads its tables. Wellness settings can turn it off, which hides its menu, pages and API without touching the rest of Pulse.

- **Scoring:** up to 8 daily-habit points a day (meals 1 each up to 3, sleep 6 h, workout 30 min, 10,000 steps, 64 oz water, meal plan), 56 a Sunday to Saturday week. Readings are stored per day, metric and source. The best value per metric counts once, so a watch and a typed entry are never added together. Days can change until the grace period after their week (3 days by default), then they lock.
- **Rules** (Wellness > Point rules) are versioned. A change starts on a date you pick, today or later, and earlier days keep the rule they were scored under.
- **Who can use it:** anyone whose permission profile has Wellness, or anyone an admin adds as a tester under Wellness > Participants (no profile change, for trying it with a few people). Other permissions: Wellness review (device exceptions), Wellness admin (participants, testers, rules) and Wellness settings. Admin starts with those three.
- **Sign-up:** Wellness is opt-in. Until a Team Member agrees on the sign-up page, only that page and the rules open; everything else (and the API) waits.
- **Activities and rewards** (Wellness > Activities and rewards): visits need a photo or PDF of a signed attendance note, InBody scans need the printout plus body fat % and skeletal muscle (lb), and weigh-ins score straight away. Notes are stored encrypted in `storage/app/private/wellness/notes` and every view is in the audit log. Reviewers (Wellness > Review queue) approve, or send back with a reason that the Team Member can fix and resend; nobody decides their own. Approved points respect each activity's cap. InBody scores when it beats the last approved scan at least 28 days earlier by the thresholds in Wellness settings.
- **Weekly reward:** `wellness:close-weeks` runs daily at 6 AM and creates a gift card for everyone with 56 daily-habit points in a week that has closed, then emails them to pick a card. Admins mark them sent or void them under Wellness > Rewards, which also has the rewards CSV and a weekly points CSV.
- **Adjustments:** from a participant's page, with a reason; they're new ledger rows, never edits, and daily points still stay within 8.
- **Test period:** points before the official start date (Wellness settings, default January 1, 2027) don't count toward prizes.
- **API:** `/api/v1` for phone apps and the Apple Health Shortcut, documented in [docs/api.md](docs/api.md). Team Members make sync keys under Wellness > Devices.
- **Apple Health:** a Shortcut on each iPhone sends steps, sleep and exercise to `POST /api/v1/wellness/apple-health` every night. Build and share it once with [docs/apple-health-shortcut.md](docs/apple-health-shortcut.md), then paste its iCloud link into Wellness settings so the Devices page offers it. `wellness:sync-check` runs daily at 10 AM and emails anyone whose device hasn't synced in 2 days, once per gap.

## Training

The Training menu replaces TalentLMS (and Trainual before it). It lives in `app/Training`, `routes/training.php` and tables starting `training_`.

- **Courses** (Training > Courses, permission Build courses): a course is lessons in order. A lesson is a page from the course designer (a word-processor style editor, Quill 2.0.3 from jsDelivr like Mermaid, so there's still no build step), a PDF, a PowerPoint, a video or audio file, a YouTube/Vimeo/Loom link (played in the page) or other link, a file to download, or a quiz. Every lesson can have designer text above it and a minimum time before "Mark as done" works. The designer's HTML is cleaned on save (`App\Training\RichText`): only formatting, links, pictures and YouTube/Vimeo/Loom players survive. Pictures are uploaded to `storage/app/private/training/images` and served at unguessable addresses.
- **Sections** (optional) group a course's lessons under named headings, such as Regulations, Policies, Procedures and Risks for a driving course. Add, rename, reorder and remove them on the course's builder page; a lesson's section is picked when it's added or on its edit page. Removing a section keeps its lessons in the course. Lessons outside any section come first. Team Members see the headings with how many lessons in each they've finished, and the AI course writer groups its pages into sections too.
- **Versions**: once a course is published it is version 1, and Team Members only ever see published versions. Editing a published lesson (its page, file, settings or quiz questions) saves a pending edit on a copy of it; new lessons wait as "not published"; removing a lesson marks it to go. The course page lists the unpublished changes with "Publish version N" and an optional "What changed" note (Discard changes / Keep it undo single items). Lesson order, sections and course details apply straight away. Publishing copies the edits onto the published lessons, so progress and grades stay attached. Team Members who finished an earlier version keep their completion; their course page shows what changed and marks updated lessons. Every visit records the first and last time each Team Member opened each version, shown under Version history.
- **Training emails** (Admin > Settings > General Settings, Training section, off by default): `php artisan training:update-emails` runs daily at 8 AM and sends each Team Member one email listing finished courses that have a newer version. While the setting is off, updates are marked as handled and never emailed later, so turning it on doesn't send a backlog.
- **Files** are stored in `storage/app/private/training` and only served to people who have the course or run training. PowerPoints show in Microsoft's free Office viewer, which fetches the file through a two-hour signed link (so the site must be reachable from the internet, and decks over about 10 MB fall back to a download; a PDF of the deck always shows). Videos stream with seeking. PHP's upload limit decides the biggest file: raise `upload_max_filesize` and `post_max_size` in cPanel > MultiPHP INI Editor for videos.
- **Quizzes**: one answer, select all that apply (all-or-nothing), true/false, fill in the blank (answers in [brackets] in the question, other accepted answers separated by |, capitals and spacing ignored), put in order (shown shuffled; drag or arrows), match by drag and drop (with a pick list for phones and keyboards), number answers with a give-or-take margin and optional unit (for dose math), tap the spot on a picture (the builder clicks the picture to mark one or more target circles), sort into groups (drag each item into its group, or pick from its list), written answers, and scenarios. A scenario isn't scored: it shows a case (text, a picture, an optional YouTube/Vimeo/Loom video) above the next N questions, which stay with it when questions are shuffled or drawn from a pool. Any question can have a picture (JPG, PNG, GIF or WebP up to 10 MB). A written answer is graded by someone with the Grade written quiz answers permission under Training > Grade answers (the attempt shows no score until then), unless the question is set so any answer gets credit. The AI course writer only writes the first three kinds. Each quiz has a passing score (default 80%), attempts allowed (blank = no limit), whether to show the right answers afterwards, question shuffling, and questions per attempt (a pool: each attempt draws that many at random, kept in the quiz's order unless shuffling is on). Every submitted attempt keeps a copy of the questions as asked, so editing a quiz never changes a grade on record. A trainer can allow one more attempt to someone who ran out.
- **Time** is counted in the browser while a lesson is in front and in use (or a video plays), and sent every 15 seconds; ten idle minutes stop the count. Each report adds at most 60 seconds and never more than has passed, so two tabs don't double it. Time reports aren't in the audit log; everything else is.
- **Completion** is lessons done ÷ lessons in the course; a quiz is done when passed. The course grade is the best score on its quiz (the average with more than one).
- **Assigning** (Training > Assign, permission Assign training): courses or a training profile, to Team Members and/or everyone on chosen permission profiles, with a due date (or each course's days to finish) and a note. **Reassign** (from a course's Progress page or a Team Member's page) keeps the old assignment and its results as history and starts a fresh one.
- **Training profiles** are bundles of courses in order (New Hire Orientation, say), separate from permission profiles. One can be given automatically to permission profiles: new Team Members on them, and anyone moved onto them, get its published courses (a main profile includes its sub-profiles), skipping courses they already have. "Give to everyone on its profiles now" catches up existing Team Members.
- **Write a course with AI** (Training > Courses, under Build courses): give a topic, who it's for, goals, anything it must cover, and optionally a PDF or text file (the handbook section or SOP), plus how many lesson pages and quiz questions. The cron job runs `php artisan training:generate` every minute, which sends it to Claude (same Anthropic key and model as the protocol import, answer held to a JSON schema) and saves the result as a **draft** course: designer pages, a quiz with the chosen passing score, and optionally the uploaded PDF as the first lesson. Pages go through the same HTML cleaning as the designer, and quiz questions that don't hold up (no right answer, two right answers on a one-answer question) are dropped. Anything Claude couldn't know is marked "[Fast Track EMS to confirm: ...]" and listed on the request page. A busy API is retried up to 5 times with a growing wait.
- **Expected time** is worked out from each lesson's content (`App\Training\Estimate`), never typed in: 200 words a minute for page text (plus 12 seconds a picture), 2 minutes a PDF page, 1 minute a PowerPoint slide (counted inside the .pptx), a video or audio file's running time (read from the MP4/MOV/M4A header or WAV format, otherwise guessed from the file size) plus 10%, 5 minutes a link, 3 minutes a download, and 45 seconds a quiz question (75 for select-all or put in order, 60 fill in the blank, 90 matching or sorting, 60 a number answer, 3 minutes a written answer, 1 minute to read a scenario; a pool counts only the questions each attempt shows). A lesson's minimum time wins when it's longer. The course's expected time is the sum, shown on My Training, the course, the builder, progress pages, the report CSV and the API. It's recalculated whenever a lesson or quiz question is saved.
- **Reference library**: every course a Team Member has finished stays on My Training to open again, and the search box there finds words in the titles and page text of their finished courses (quiz questions are not searched), with the matching passage highlighted.
- **Reports** (Admin > Reports > Training Reports, permission Training reports): filter by course, Team Member, position, status and assigned dates; CSV of assignments and of every quiz attempt.
- **Page blocks** (`App\Training\Blocks`): the designer's Add buttons insert a step-by-step (one step at a time with Back/Next), two columns (half and half or a third/two thirds; they stack on a phone), a callout box (note, tip, important, safety) or a question (one answer, select all, true/false, fill in the blank). A block is stored inside the page as `<div class="tblock" data-kind data-block="{json}">`, so versions copy it, and it is checked and rebuilt on every save (blocks can't sit inside blocks). A question is checked by the server, so the right answer never reaches the browser; Team Members can try until they get it, answers are kept in `training_block_answers`, and a question marked "must answer" holds back "Mark as done". The designer also has fonts (serif, typewriter, condensed), line spacing and paragraph gaps.
- **Quiz retake wait**: a quiz can make Team Members wait minutes, hours or days after a try that doesn't pass.
- **Assignments** (lesson kind): the page explains the task and Team Members hand in a written answer and/or files (up to 10, 100 MB each, kept in `storage/app/private/training/submissions`). Someone with the grading permission approves it, which finishes the lesson, or sends it back with a comment, under Training > Grade answers.
- **SCORM packages** (lesson kind, permission Upload SCORM packages, Admin only at first, because a package runs its own code inside Pulse): a SCORM 1.2 or 2004 zip from Articulate, Captivate, iSpring and the like is unpacked next to its zip, and `imsmanifest.xml` names the start page. The lesson plays it in a frame with a SCORM API (`public/js/scorm-api.js`) that saves what it reports, including where they left off; completed/passed finishes the lesson and the score counts as its grade.
- **In order**: a training profile can open its courses one at a time; the next opens once the one before is finished.
- **More page blocks**: tabs (arrow keys move between them; on a phone they still work as tabs), expandable sections, flashcards (flip, back/next, shuffle), process diagrams (across or down; across stacks on a phone) and charts. A chart is columns, bars across or a line, up to 4 series and 24 labels, drawn as SVG on the server (`App\Training\Chart`, no chart library): the value axis starts at zero, hovering a mark shows its value, and "Show the numbers" opens a table. The colors are checked for color blindness. On a phone a chart keeps its text size and scrolls sideways.
- **One lesson at a time** (course setting, off by default): each lesson opens once the one before it is finished; locked lessons show a lock.
- **Timed quizzes** (quiz setting, blank = no limit): a countdown shows during the attempt and answers are saved every few seconds and as they change (`training_attempts.draft`). When time runs out the page hands the quiz in. If the page was closed, the attempt is handed in with the saved answers the next time the quiz is opened, and answers sent more than a minute after the time are not counted. Attempts and the attempts CSV show "Time ran out".
- **Feedback after each question** (quiz setting): each question has a Check button that shows right or wrong, the explanation and (if the quiz shows answers) the right answer. The checked answer is then fixed for that attempt.
- **Surveys** (lesson kind): rating 1 to 5 (with optional end labels), pick one, pick any, or a written answer, each optionally required. Sending the answers finishes the lesson. An anonymous survey keeps the answers in `training_survey_responses` without a name, and the audit log entry leaves the answers out. Builders and report readers see totals, averages and written answers, with a CSV, from the lesson's "See the results" link.
- **Skills checklists** (lesson kind): a list of skills (some marked critical) that someone with **Sign off skills** (`training_signoff`) checks off in person from Training > Sign off skills: each item Done or Not yet with a note, signed with a tick box. Every check is kept in `training_skill_checks`; the lesson finishes when every item is done. Nobody can check off their own skills.
- **Sign-off required** (any other lesson): finishing it (Mark as done, a passed quiz, an approved assignment, a survey, SCORM or a scenario) waits in Training > Sign off skills until a trainer signs it off (`signoff_requested_at`, `signed_off_at`, `signed_off_by` on the lesson progress).
- **Branching scenarios** (lesson kind): scenes with choices that lead to other scenes, optional feedback per choice, and endings marked good, bad or neutral. The server checks the path is real. Reaching an ending finishes the lesson, or only a good ending when the builder asks for it; the last 50 runs are kept.
- **Questions in a video** (uploaded videos): each pauses the video at its time and must be answered right to finish (checked like page questions, stored in `training_block_answers`). **No skipping ahead** stops seeking past what's been watched.
- **AI for Team Members** (course setting, only for people with **Create AI-based training**, `training_ai_courses`): an **AI coach** on the course page that answers from the course's page text (conversation kept in `training_ai_messages`), and **AI practice questions** (5 at a time, ungraded, in `training_ai_practice`). Limits: tokens per Team Member per course (the course's own number, or Admin > Settings "Team Member AI: tokens per course", default 50,000) and per Team Member per month across courses (default 300,000); 0 = no limit. All usage shows in Admin > Reports > Training AI Usage.
- **AI pictures and video questions** (builders with **AI content development tools**): "AI picture" in the designer draws a simple SVG diagram, cleaned by `App\Training\Svg` (shapes and text only) and served with a sandbox CSP; video lessons can get AI questions from a pasted transcript. Both count toward the builder's monthly AI limit.
- **Course rules** (course details, each off by default):
  - **Certificate**: a printable certificate on completion (Print saves it as a PDF), numbered FT- plus 10 letters and digits. Anyone can check a number at `/training/verify` without signing in. Turning certificates on later gives them to people who already finished.
  - **Expiry and renewal**: a completion counts for N months. `training:daily` (7:30 AM) assigns the course again N days before it expires (30 unless set), due on the expiry date, and the finished one stays on record. Changing the months updates people who already finished.
  - **Scheduled publish and retire**: `training:schedule` (every 5 minutes) publishes a draft, or a published course's unpublished changes, at the publish time, and sets the course to Archived at the retire time.
  - **Acknowledgment**: a statement Team Members sign (tick the box and type their name) to finish the course. Every signature is kept in `training_acknowledgments` with the statement as it read, the version, the time, the IP and the browser. With **sign again on updates**, a new version asks people who finished to sign again: it shows on My Training and in the menu count as "Acknowledge the update", the course page shows what changed, and the earlier signature stays.
  - **Ratings**: 1 to 5 stars and a comment after finishing. The average and comments show on the course's builder page, and in the report CSV.
- **Reminder emails** (Admin > Settings > General Settings, Training section, sent only while training emails are on): one email per Team Member listing courses due within N days (default 3), and courses overdue, repeated every N days (default 7). 0 turns either off. Changing a due date resets its reminders.
- **AI permissions**: "AI content development tools" (the course writer, AI writing help in the designer, AI quiz questions) and "Create AI-based training" (for the Team-Member-facing AI coming next) are separate from Build courses. **AI writing help** writes new text, rewrites, simplifies, shortens or expands the selection, or adds key points. **AI quiz questions** reads the course's page text and adds the questions to the end of the quiz to be checked. Every AI request is recorded in `training_ai_usage`; **Admin > Reports > Training AI Usage** (Training reports) shows tokens and a rough cost by person, course and tool. Builders' monthly limits are set there: per permission profile (blank = unlimited), and per person (follow the profile, unlimited, or their own number; changing them takes the Permission Profiles permission). At the limit the AI tools stop until the 1st.
- Permissions: Training (take courses), Build courses, Assign training, Training reports, Grade, AI content development tools, Create AI-based training, Upload SCORM packages. Admin starts with all of them; tick Training on Team Member (and other profiles) to open it to everyone.
- **API:** `/api/v1/training/...`, see [docs/api.md](docs/api.md).
- **Moving from TalentLMS** (`App\Training\Import`): the courses are pulled out of TalentLMS into an export folder (manifest.json, one courses/<id>.json per course, and files/ with every picture, PDF, PowerPoint and video), then brought in on the server with `php artisan training:import-talentlms /path/to/export` (`--dry-run` to preview, `--course=141` for one course). Each course arrives as a **draft** with its sections, pages (formatting converted: bold/italic/underline set by styles, text sizes, colors and highlights, alignment, indents, picture sizes and centering, tables), files, YouTube videos and quizzes; Team Members don't see a draft or its history until it's published. TalentLMS enrollments become assignments marked "Imported from TalentLMS" with their dates, time, progress, lesson completions and quiz scores; publishing the course counts finished ones as finishing version 1. Team Members are never created: people are matched by email, else by first and last name when exactly one Team Member has it, and everyone else is listed in `storage/app/private/talentlms-not-in-pulse.csv`. A course already imported is skipped, so it can run again. TalentCraft and SCORM units can't come over and are listed.

## Trip Board (non-emergency transports)

Dispatch > Trip Board books and runs stretcher transports: dialysis, appointments, discharges and transfers. Trips are booked from the intake form (one way, a round trip with a linked return leg, or a standing order repeated on chosen weekdays for up to 26 weeks), wait in the Unassigned queue (ASAP, Scheduled, Will-call) and are dragged onto a truck's 15-minute timeline. The columns are the trucks Vehicle Assignments has on the road that day, with their crews and shift times.

- **Assigning** checks the crew's level against the trip (ALS level or ALS equipment on a BLS truck), out of service, the truck's shift and overlapping trips. Any of those asks the dispatcher to confirm, and the confirmation is in the trip's history. Every change carries the trip's version; a second dispatcher working from an old copy gets "someone else changed this" instead of overwriting it.
- **Live updates:** the board asks `/trips/changes` for new events every 4 seconds (`trip_events`; there is no websocket server on cPanel). Other dispatchers' changes show as toasts. New ASAP trips and late trips beep and can raise a desktop notification without patient names.
- **Intake** records the call (ordering facility, caller, callback phone, priority), the pickup and destination with department, room and phone, ICD-10 diagnoses (type a code or words; the first is primary), oxygen liters, stairs, riders, DNR, referring and receiving doctors (NPI), and PCS on file / requested / signed. Tabbing off the patient's name or date of birth looks them up, so a patient on file isn't typed in twice. An ASAP trip can carry a **quoted time** (what the caller was told): it isn't a pickup time, so the trip stays ASAP and only shows late after the quote. Scheduled trips are late after their pickup time. A round trip's return can be will-call, a set time, or wait-and-return (the crew stays).
- **Patients** (Dispatch > Patients): the record intake fills from: name parts, address, contacts and next of kin, primary care doctor, MRN, the facility they live at, baseline and dispatch notes (shown at intake and to the crew), extra loading minutes, paperwork (PCS and prior auth dates), usual level and equipment, and every past and scheduled trip. Missing, expired or expiring paperwork shows on the trip cards.
- **Payors:** one shared list (`trip_payers`), so an insurance company is listed once. On a patient, "+ Add payor" adds a row with a type-to-search box; a payor that isn't on the list is typed straight in and added once (matched ignoring case, spaces and punctuation). Rows are in billing order (primary, secondary, tertiary) with member id, group, policy holder, effective dates and eligibility check. Supervisors tidy the list on Dispatch > Payors: rename, set the kind and electronic payer id, turn one off, or merge a duplicate into the one to keep.
- **GPS:** trucks report through the webhook `POST /api/trips/gps` (key from Trip Settings; generic JSON or Traccar), through Samsara (token in Trip Settings, read every minute by `trips:samsara`), or a crew phone (My Trips). Trucks whose device id starts with `SIM-` are moved by the simulator when it is on. Loaded miles are measured from the breadcrumbs between Transporting and At destination. Positions older than a day are deleted nightly (`trips:prune-gps`).
- **My Trips** is the crew's MDT on a phone or tablet: the truck's status (available, at station, fuel, meal, cleaning, out of service, shown on the board), the current trip with rooms, phones, directions, diagnoses, equipment, baseline and notes, one big button for the next status, odometer readings (they give loaded miles when GPS didn't) and a note back to dispatch.
- **ePCR import from CAD:** billing is done from the ePCR, so this is how trip data leaves dispatch. The ePCR pulls `GET /api/trips/epcr/trips?since=…` with the `X-EPCR-Key` header (key from Trip Settings) and gets every trip a truck has that changed since then, as XML with NEMSIS 3.5 element names (or JSON with `format=json`); dispatch details without a NEMSIS element are under `<PulseDispatch>`. Code values and the import format depend on the ePCR vendor. Dispatchers can download one trip's file from the trip drawer. Both are in the audit log by trip number.
- **Trip Map** shows trucks (free, on a trip, no recent GPS), facilities and trips waiting for a truck. Tiles come from `TRIPS_MAP_TILE_URL` (OpenStreetMap by default); Leaflet loads from jsDelivr.
- **Reports** (Dispatch > Trip Reports): counts, on-time pickups, ASAP response, ASAP trips on scene by their quoted time, truck busy hours and loaded miles, with a CSV, and no patient details. Printable run sheets contain patient details, need their permission and are in the audit log.
- **Patient information:** names, dates of birth, contact details, member ids, MRNs, complaints, diagnoses, rooms, notes and addresses are encrypted columns (`APP_KEY`). Patient searches are POSTed so names never land in a URL or a server log. The audit log records who opened which trip or patient by number only. People with "See the Trip Board" only see initials and "Residence" for home addresses. Trip pages sign out after Trip Settings' idle minutes (`TripsIdle`).
- **Practice data:** `php artisan trips:sample you@example.com` adds made-up facilities, five trucks with today's crews (you are added to the first one), nine patients and their trips. Add `--force` on a production install.

Permissions (Admin only at first): "See the trip board", "Dispatch trips", "My Trips", "Trip reports" and "Trip supervisor". Give Dispatchers "Dispatch trips", crews "My Trips", and supervisors "Trip supervisor" and "Trip reports" in Admin > Permission Profiles.

## Help

The blue **?** in the nav bar opens the Help directory (`/help`), grouped by module (Getting started, Draw Box, Protocols, Training, Supplies, Service Desk, Wellness, and more to come). Lessons are listed in `config/help.php` under their module, and each lesson is a Blade file in `resources/views/help/lessons/<slug>.blade.php` with its screenshots in `public/images/help/<slug>/`. `<x-help.step>`, `<x-help.shot>` and `<x-help.tip>` give the numbered steps, pictures and tip boxes.

Team Members only see help for what they can use. A module's lessons show only when that module's menu shows for them in the nav bar (the checks are in `app/Help/Access.php` and must match the nav), and a lesson can also need its own `permission`. Hidden lessons are left out of the directory and search, and their links answer "not found". A lesson can be marked `public` (readable before signing in; only for sign-in help). Inside a lesson, wrap a paragraph about an extra permission in `@if (auth()->user()?->hasPermission('...'))`.

## Deploy on cPanel

1. **PHP:** in WHM's MultiPHP Manager, set the subdomain to PHP 8.3 or newer. It needs the extensions `pdo_mysql`, `mbstring`, `openssl`, `tokenizer`, `xml`, `ctype`, `fileinfo` and `bcmath`.
2. **Subdomain:** create `drawbox.fasttrackems.com` in cPanel and set its document root to `drawbox/public`. Run AutoSSL so it gets a certificate.
   > The document root must be the `public` folder, never the project folder itself. Otherwise `.env`, with its database and mail passwords, can be downloaded from the web.
3. **Database:** create a MySQL database and user in cPanel, and give the user all privileges on the database.
4. **Mail:** the app sends mail as `drawbox@fasttrackems.com` through Google Workspace. Sign in to that account, turn on 2-Step Verification, and create an App Password at myaccount.google.com/apppasswords. In WHM, go to Security Center, then SMTP Restrictions, and make sure it is **disabled**. When it's on, cPanel blocks connections to Gmail.
5. **Code:** in cPanel's Git Version Control, clone this repository into `~/drawbox`. Then, in cPanel's Terminal (cPanel's jailed shell has no `composer` command, so download a copy into the project; it's git-ignored):
   ```sh
   cd ~/drawbox
   php -v    # must say 8.3 or newer; if not, use the full path below in place of "php"
             # /opt/cpanel/ea-php83/root/usr/bin/php
   curl -sS https://getcomposer.org/installer | php
   php composer.phar install --no-dev --optimize-autoloader
   cp .env.example .env
   php artisan key:generate
   ```
   Edit `.env`:
   ```ini
   APP_ENV=production
   APP_DEBUG=false
   APP_URL=https://drawbox.fasttrackems.com

   DB_CONNECTION=mysql
   DB_HOST=localhost
   DB_PORT=3306
   DB_DATABASE=cpaneluser_drawbox
   DB_USERNAME=cpaneluser_drawbox
   DB_PASSWORD=...

   MAIL_MAILER=smtp
   MAIL_HOST=smtp.gmail.com
   MAIL_PORT=587
   MAIL_SCHEME=null
   MAIL_USERNAME=drawbox@fasttrackems.com
   MAIL_PASSWORD="the 16-character app password"
   MAIL_FROM_ADDRESS=drawbox@fasttrackems.com
   ```
   Then:
   ```sh
   php artisan migrate --force --seed
   php artisan drawbox:ssn-key    # the key that encrypts SSNs; back it up apart from the database
   php artisan drawbox:make-admin you@fasttrackems.com "Your Name"
   php artisan config:cache && php artisan route:cache && php artisan view:cache
   ```
6. **Cron:** in cPanel's Cron Jobs, add a job that runs every minute. It expires overdue draws and sends the new-draw emails (every 2 hours) and reminder emails.
   ```
   * * * * * cd ~/drawbox && php artisan schedule:run >> /dev/null 2>&1
   ```
   If `php -v` showed an older version, use `/opt/cpanel/ea-php83/root/usr/bin/php` in place of `php` here too.
